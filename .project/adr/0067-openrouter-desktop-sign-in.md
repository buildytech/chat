# ADR 0067: Sign in with OpenRouter on the desktop app

Status: accepted, 2026-11-23 (owner t136u); phase 1 (contract) 2026-11-23.

## Context

The desktop app (`buildytech/buildychat-desktop`, ADR 0065) needs the owner's xAI key in the OS keychain. The owner wants a sign-in instead, with the same Grok models for text and pictures, and only on the desktop: the web version stays on xAI, unchanged. Research t135u (`/workspace/buildy-chat-shots/t135u-pkce-research.md`) compared OpenRouter and OpenAI: OpenRouter documents an OAuth PKCE flow for any app (no client registration, `localhost` callbacks on any port, the result is a user-controlled API key billed to the user's credits; https://openrouter.ai/docs/guides/overview/auth/oauth), OpenAI's "Sign in with ChatGPT" for third-party apps has no image generation and a different wire. OpenRouter serves `x-ai/grok-4.20` (reasoning off unless asked), `x-ai/grok-4.7` (reasoning mandatory) and `x-ai/grok-imagine-image-2.0` (POST /api/v1/images, synchronous, base64 answers) over an OpenAI-compatible Chat Completions API with tool calls (live checks t136u phase 0).

## Decision

1. **Desktop only.** Every OpenRouter route and status field is a `desktop` case. The web runtimes answer 404 on the new paths and send no `provider` in status (tested); the web app keeps its xAI code path.
2. **Sign-in, loopback, PKCE S256.** `POST /runtime/v1/auth/openrouter/start` makes a 32-byte verifier, its S256 challenge and a 32-byte state, opens a one-shot HTTP listener on `127.0.0.1` (and `::1`) on a random port and opens the system browser (Wails `app.Browser.OpenURL`) at `https://openrouter.ai/auth?callback_url=http://localhost:<port>/cb/<state>&code_challenge=…&code_challenge_method=S256`. The state rides in the callback path because OpenRouter documents no `state` parameter; the listener accepts `GET /cb/<that state>?code=…` once, within 10 minutes, then closes. The code is exchanged at `POST https://openrouter.ai/api/v1/auth/keys` with the verifier; the key goes to the OS keychain under its own item (the xAI key item is untouched). `POST /runtime/v1/auth/openrouter/signout` deletes it. No custom URL scheme (a bare exe registers none). The key, the verifier and the code never reach the webview, a log or an answer.
3. **Provider choice.** Signed in with OpenRouter, the desktop serves with OpenRouter (it wins over an xAI key); otherwise xAI as before (the keychain xAI key stays the fallback). Status reports `provider: { id, signedIn, pending }` (`provider.schema.json`) and `capabilities.signIn: ["openrouter"]`. The readiness fields and codes are the same as for xAI, so the readiness logic of the app does not fork; with OpenRouter, `models` holds the allowed models OpenRouter lists (`/models`, `/images/models`) and the candidate is `x-ai/grok-4.20`.
4. **Forward.** `POST /runtime/v1/openrouter/chat/completions` follows the xAI forward's rules (placeholder key replaced, one path and method, 256000 bytes, no redirect, key redacted) and accepts only `constants.openrouter.chatModels` that OpenRouter lists (never the image model). The webview's `x-grok-conv-id` is sent as `x-session-id` (OpenRouter's sticky routing keeps Grok's prompt cache warm). The answer, `usage.cost` included, passes through; the app reads the cost.
5. **Pictures.** With OpenRouter, `generate` of `/runtime/v1/media` makes one synchronous `POST /images` call (`response_format: "b64_json"`), stores every decodable picture in the local store at once and answers `status: "done"` with local file addresses and the cost in xAI ticks (USD × 1e10). The app accepts a done generate without polling. Signed URLs of OpenRouter (storage.googleapis.com, 24 h) are not used. Encode, asset and the ZIP export are unchanged.
6. **Headless.** The `-tags server` build reads `OPENROUTER_API_KEY` from the environment (tests and the exam), as it reads `XAI_API_KEY`.
7. **Constants.** `packages/provider-xai/src/openrouter.ts` is the source; `npm run contract:runtime` writes `constants.json` `openrouter`; the Go host reads it from the pinned submodule.

## Consequences

The desktop gains a second provider without a second agent: the same loop, prompts and gates run in the webview, only the base path, model ids and the reasoning flag differ. Owners pay OpenRouter's price (Grok list price plus OpenRouter's fee) from their own credits. Whether OpenRouter's auth page accepts `127.0.0.1` callbacks could not be verified without an account (every callback form redirects a signed-out browser to sign-up), so the callback uses the documented `localhost`; the listener binds both loopback families. Live checks that need a key (reasoning flag, `parallel_tool_calls`, `max_completion_tokens`, base64 pictures) run from `/workspace/tools/t136u/orcheck.mjs` once the owner provides one.
