# ADR 0033: Actionable edit_page rejections, add of catalog blocks, bounded Build loop and the Ask plan trigger

Status: accepted, 2026-11-13. Replay of the owner's session of 13.11 (a Stock teams page of six blocks, Ask run on grok-4.20-0309-non-reasoning, then "go ahead" in Build: 8 steps, ~107k prompt tokens, nothing applied, "codes use_edit_page, page_patch_invalid; paths $.newPage, $.ops[7].field").

## What went wrong

1. Ask answered with replace / add recommendations in prose and the plan card never appeared. `propose_plan` is optional (`tool_choice: auto`), and the one forced follow-up (ADR 0020) only fired when the answer contained a block id as text. The model named blocks by their catalog names and had read the specs of the blocks it recommended through `get_block`; there was no id in the prose, so no plan and no Apply in Build button.
2. The recommended ops could not be expressed. On this page the Logo cloud and the Testimonials are two blocks of the same page kind (`features`). `add` took only a kind, so adding Steps or Pricing was `block_exists`; naming `catalogBlock` on `add` was `page_patch_invalid` (additionalProperties), the contract allowed it on `replace` only. `edit_page` did not even list `catalogBlock` in its tool definition.
3. A schema rejection said `page-patch/v1 enum failed. Send ops only (...)` with one path. Not the op index, not the op, not the keys or the enum the key allows. The model resent all eight ops five times. One bad op rejects the whole patch (all or nothing) and nothing repaired it (the host repair of ADR 0018 existed for `propose_layout` only).
4. `propose_layout` on a current page returns `use_edit_page`; the model called it again at step 7. Nothing capped repeated identical rejections: the loop ran the whole budget.

## Decisions

- Contract (ui8kit/contract c351cdb, page-spec 1.5.0, additive): page-patch/v1 `add` takes an optional `catalogBlock`, a Stock catalog block of the given `kind`. With it the page may hold several blocks of one kind; without it `add` is unchanged (the page's sample block of the kind, `block_exists` when the page has one). The host checks kind (`catalog_block_kind_mismatch`), variant (`unknown_variant`), renderer, the header / footer slot rule (`addSlotCheck`, now in `page-slots.ts` with the id helpers, shared with the inspector) and gives the new block a fresh id. Plan ops (`add`) carry `catalogBlock` as `replace` does (session shape unchanged: the plan op already has the property). `kind` may be left out when `catalogBlock` names the block.
- Rejections the model can act on: a schema rejection becomes one report per rejected op (`patchIssueReports`): index, op, key, the keys the op takes and requires, or the allowed enum values. `edit_page` replies carry `opIndex` and `fix` (invalid ops, allowed values, existing block ids); every runtime rejection message starts with `ops[i] (op blockId)`. Tool definitions and the Build prompt list `catalogBlock` and `at` for add / replace and say that `field` belongs to set and set_page only.
- Repair like ADR 0018: the same op rejected twice in a turn (`sameRejection`: same code, same `$.ops[i]`) is left out by the host, the rest runs and each skipped op is said in the proposal warnings (`acceptEditPartially`, at most 3 ops, an op that depended on a skipped one is skipped too). Scope rules are unchanged: remaining ops pass the same gates. The author still applies the proposal.
- Loop guard: the same rejection twice in a row with no host repair ends the turn ("Stopped on the same rejection twice; the rest of the step budget was not spent." plus the host's own last message). After the first `use_edit_page` only `edit_page` is offered for the rest of the turn.
- Ask plan trigger: next to a block id in the answer (forces `propose_plan`, as before), the model having read a catalog block the page does not have (the prompt makes it call `get_block` for every block it discusses, so this is a replace / add candidate) offers `propose_plan` once with `tool_choice: auto`; the model may decline (a plain catalog question about a block of the page costs no extra step). Program data only: ids and tool results, never words of the answer. The plan card has the Apply in Build button; Build never reads Ask prose or acceptance phrases (ADR 0020 is unchanged).

## Consequences

The owner's flow ends in 3 steps instead of 8 even when the model repeats a bad op, with the valid ops applied and the skipped one named. An Ask recommendation to replace and add blocks yields a checked plan card. A page can hold several blocks of one kind through `add` with `catalogBlock` (Build, Ask plans), as the inspector and Blocks feed already allow. Not solved: a model that names no block at all and reads no catalog block gets no plan card; the author asks again or edits by hand.
