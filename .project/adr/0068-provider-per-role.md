# ADR 0068: A provider per role, approved models, and a Settings screen

Status: accepted, 2026-11-23 (owner t138u, narrowed from the t137u design; t139u: its own Settings screen); phase 1 (contract), phase 2 (desktop host and menu) and phase 3 (app) 2026-11-23.

Extends [0065](0065-runtime-http-contract.md) and [0067](0067-openrouter-desktop-sign-in.md). Supersedes 0067 decision 3 ("OpenRouter wins over an xAI key") for the app's choice; the status top-level fields keep 0067's meaning.

## Context

Signed in with OpenRouter, the desktop sent every chat turn *and* every picture to OpenRouter. The owner wants to choose per role: for example Build through OpenRouter while Media draws with the xAI API, and OpenRouter pictures off for now (t136u spent the $5 key limit on pictures in four pages). The owner also wants to approve, per provider, which models may be used at all, as a plain list for now, so another drawing model can be approved later.

## Decision

1. **Roles.** Build and Ask (chat models) and Media (image models). Ask defaults to "Same as Build". Each role has a provider and a model; Media can also be **Off** (no pictures are drawn; blocks keep placeholders and descriptions). Defaults: Build on the host's first ready provider (OpenRouter on a desktop signed in with it), Ask same as Build, Media on xAI with 3 variants per picture as before, Media off when no xAI key is there. The app never switches provider by itself.
2. **One Settings screen.** A separate route of the app, `/settings`, holds everything: one row per role (provider, model, state, spent), the approved-model lists per provider and kind (one textarea each, one id per line), and on the desktop the xAI key field and the OpenRouter sign-in / sign-out (moved there from under the composer). Nothing else in the chat UI changes. The browser reaches it by a link where Settings live today; the desktop opens it from its native application menu, "Settings…" with CmdOrCtrl+, (the main window navigates to the route). Desktop and browser render the same screen; rows a host cannot serve say so ("Desktop app only", "No key on this computer").
3. **Status `providers`** (desktop): one entry per provider, `id`, `state` (`ready`, `not_configured`, `limit`, `unavailable`), `key` (`present`, `source`), `roles` the host serves with it (`constants.providers.roleSupport`; OpenRouter has no `media` while `constants.openrouter.mediaEnabled` is false), `models` (`chat`, `image`: what the host serves with that key, discovered with that key) and, for OpenRouter, `pending`. Both providers are discovered when both keys exist. The top-level fields (`ready`, `models`, `provider`, …) keep their ADR 0067 meaning for older apps. Web hosts send no `providers`; the app reads them as one xAI entry from the top-level fields.
4. **The host enforces, the list narrows.** Keys stay in the host. Text goes by route (`/runtime/v1/xai/…`, `/runtime/v1/openrouter/…`); media names `provider` (absent = `xai`, never "whatever key is there") and optionally `model`. The host refuses: an unknown provider (422 `invalid_request`), a provider whose role is off (409 `provider_role_disabled`: OpenRouter pictures today, on every host), a model of the wrong kind or another provider's (422 `model_not_allowed`), a provider without its key (503 `xai_api_key_missing` / `openrouter_key_missing`, no fallback), a model outside the provider's allowlist or discovery (422 `model_not_listed`), and (desktop) a model outside the owner's approved list (403 `model_not_approved`, checked before any provider call). Approving never widens: an approved id the host does not serve, or of the wrong kind, stays refused.
5. **Where the approved lists live.** Desktop: in the host's config (`providers.json` beside the picture store), read and written by `GET`/`PUT /runtime/v1/settings/providers` (`{ approved: { xai: { chat, image }, openrouter: { chat, image } } }`; a list is `null` = not narrowed, or ids; trimmed, no blanks or repeats, at most `constants.providers.approved.maxIds`, each matching `idPattern`), so the host enforces them. Web: the same document in this browser's storage (`buildy:v1:approvedModels`); the web runtime enforces its own catalog and the hard rules, the per-device list narrows the app's choices (a shared web runtime has no per-user state).
6. **Role choice storage.** Per device (`buildy:v1:providerRoles`), not per page; the session records what each run actually used, inside the fields the session schema already has: the role is the assistant message's `mode`, the provider `run.usage.providerId`, the model `run.modelId`, the cost `run.usage.cost`; a drawn slot keeps `provider` and `model` in `ext.media`. An export stays honest without a session schema change.
7. **Limits.** A 402, or a 403 whose body names a key/credit/spending limit, is `provider_limit` (`isProviderLimit`, shared by the web runtime, the webview's turn and the Go host). The desktop remembers it per provider for `limitTtlSeconds` (600) and reports `state: "limit"`; a later success clears it. The Settings row reads "Limit reached"; nothing switches by itself.
8. **xAI key on the desktop.** `PUT /runtime/v1/keys/xai { key }` stores the trimmed key (one token, at most `xaiKeyMax`) in the OS keychain; `DELETE` removes it; there is no `GET`. No answer, log or status ever contains it. `capabilities.keys: ["xai"]`, `capabilities.settings: ["providers"]` tell the app to show the field and to use the host's lists.
9. **Media pace.** Media draws at most `MEDIA_SLOT_CONCURRENCY` (2) slots at a time.
10. **Cost per role.** The spent amount of a row is the sum of the billed ticks (`usage.cost` from OpenRouter, `cost_in_usd_ticks` from xAI, the draw's `costUsdTicks`) of that role's runs and draws on this device since the last "Reset spent" (`buildy:v1:providerSpend`, per role and provider). A per-device ledger, not the current chat: the Settings screen is its own route and opens no project. Unbilled runs add nothing (missing cost is unknown, never zero).

## Contract (phase 1)

`constants.json`: `openrouter.mediaEnabled`, `providers` (ids, roles, kinds, roleSupport, limitTtlSeconds, approved, xaiKeyMax), generated from `packages/agent-manifests/src/roles.ts`. Cases: `media-provider.json` (17), `provider-settings.json` (12), `keys-xai.json` (8), `status.json` (+8, one changed: both keys discover both), `xai-forward.json` (+3), `openrouter-forward.json` (+4); `media-openrouter.json` now names `provider: "openrouter"` and runs with `env.openrouterMedia` (the switch on) so the draw stays covered. Runner fields (desktop): `env.openrouterMedia`, `env.limited`, `env.approved`, `expect.limitedAfter`, `expect.approvedAfter`, `expect.xaiKeyAfter`. Schemas: `providers.schema.json`, `provider-settings.schema.json`, `capabilities.schema.json` (`keys`, `settings`).

## Desktop host (phase 2)

`internal/runtime/roles.go`: the providers of the status, the limit memory, the approved document (`<UserConfigDir>/BuildY/providers.json`, written atomically) and the settings and keys routes; media dispatches by `provider`; the forward checks the approved list before discovery. `cmd/buildychat/menu*.go`: the application menu (macOS: the app menu with About, Settings…, Hide, Quit; elsewhere a File menu with Settings… and Quit; Edit, View and Window roles), "Settings…" / "Настройки…" by the system locale (`LC_ALL`, `LC_MESSAGES`, `LANG`, `LANGUAGE`), CmdOrCtrl+,; a click navigates the main window to `/settings` and focuses it. The headless server build has no menu.

## App (phase 3)

- `/settings` (`src/routes/settings`) renders the core `SettingsScreen`: a header (back to the builder, the dark switch) and the `settings.screen` slot (`SlotProps`); the core alone says there is nothing to set. The sidebar's Settings region links to it when a module fills the slot.
- The chat module's `ProviderSettings` fills it: the role rows (UI8Kit `Select`, `Badge`, `Text` in an 8+4 grid; each row a `group` labelled by its role; selects labelled "Provider for Build" etc.), one textarea per provider and kind the host serves (empty = not narrowed; saved through the host on the desktop, else in this browser), the desktop's xAI key field (password input, never prefilled, Save / Remove) and the OpenRouter sign-in (moved from under the composer). Texts in `modules/chat/i18n/{en,ru}.json`.
- `browser/provider-roles.ts` (pure): `providerViews`, `parseApprovedText`, `chatChoices` / `imageChoices` (served ∩ approved; OpenRouter chat lists name OpenRouter ids, the app keeps its own), `roleProvider` (defaults, no switch), `roleStatus` (the status a role's turn runs against: that provider's readiness, key, approved app ids and `provider.id`, so the webview's turn takes that wire), `mediaModel`, the spend ledger. `browser/providers.svelte.ts` keeps the state; a turn notes the status, runs on its role's status, tags `usage.providerId` and adds its billed cost; the Build role's models narrow the composer's selector (the Build model stays `selectedModelId`).
- Media sends `provider` and `model`, draws `MEDIA_SLOT_CONCURRENCY` slots at a time, and with Media off (or no approved picture model) draws nothing and says where to change it.
- Tests: `scripts/m4-api-tests/provider-roles.test.ts`.

## Consequences

The owner can run Build on OpenRouter credits and Media on the xAI account, approve models without a release, and turn pictures off. OpenRouter pictures need one constant flipped (and its cases already exist). A status on a desktop with both keys costs two discoveries. The web's approved lists are per browser. The menu label follows the process locale, not the app's language setting. The web keeps one provider; the screen shows the other as desktop-only.
